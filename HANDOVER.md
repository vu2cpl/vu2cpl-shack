## Known weirdness

- `~/Documents` on this Mac is **local**, not iCloud-synced. Only `~/Desktop` symlinks to iCloud Drive. The 05-07 folder consolidation was for organizational tidiness only.
- `/home/vu2cpl/as3935_mqtt.py` had become **owned by root** during earlier sudo edits — `cp` without sudo silently no-op'd. Always check ownership after first deploy. Fix: `sudo cp + sudo chown vu2cpl:vu2cpl`.
- AS3935 with NF=0 fires a noise burst at startup (~209 events in 30 s) then the chip's auto-noise-track suppresses further until conditions actually change. NF=4 is the production default; NF=0 only for diagnostics.
- **DXCC blacklist has no off-Pi backup since 2026-05-13** ([`b1fbef9`](https://github.com/vu2cpl/vu2cpl-shack/commit/b1fbef9) public-prep). `nr_dxcc_blacklist.json` is `.gitignore`d to avoid publishing the muted-callsigns list. Deliberate trade-off — accept that a Pi disk failure means the list evaporates and gets repopulated from memory. List is small (<20 entries typically), recoverable. If it ever grows large enough to be painful to lose, set up a periodic rsync to the Mac. Same `.gitignore` reasoning applies to `nr_dxcc_seed.json` and `nr_lightning_events.jsonl`, but those are runtime caches — Club Log / AS3935 events recreate them naturally, no loss.
- **A stale Node-RED editor browser tab can silently revert `flows.json` on Deploy** — discovered 2026-07-13 (SHACK_CHANGELOG same date). Deploy always pushes the *deploying* tab's full in-memory flow model to disk; if that tab has been open since before other changes landed (via a different tab, `nrsave`, or a direct file edit), those changes get clobbered with zero warning. Symptom looks like a huge, confusing `git diff --stat` (thousands of lines) that's mostly Node-RED's own harmless key-reordering — the real damage (a handful of dropped wires / reverted fields) hides inside it. Before deploying from any editor tab that's been open a while, hard-refresh it first. To diagnose after the fact: diff `flows.json` **by node id** (`{id: node}` dict, ignoring key order) against the last commit rather than trusting the raw stat. **Recurred 2026-07-31** with a near-identical diff stat (3016+/3069−, same as the original), almost certainly the *same* never-closed tab — "hard-refresh it first" evidently isn't a reliable enough mitigation on its own. Fast triage signal from the repeat: if `/shack` breaks but `/ui` still works, check `uib_shack_01`'s reference count first (`grep -c uib_shack_01 flows.json` vs `git show HEAD:flows.json | grep -c uib_shack_01`) — D1 has no shared choke point so this class of bug can't touch it, while every Vue card routes through that one node. **Recurred twice more 2026-08-21** (wipes #3 + #4 — the fourth from the operator's *only* open tab, proving this is a single-tab hazard: the tab went stale when the morning's fix landed via git pull + restart underneath it; the fourth also got committed, forcing a semantic rebuild instead of `git restore`). Now guarded by **`flows_guard.py`** (pre-commit hook Pi + Mac + 1-min Telegram cron) — see CLAUDE.md critical rule #7 and SHACK_CHANGELOG 2026-08-21. **Final resolution 2026-08-21:** staleness was never the root cause — the editor was stripping 30 hand-added **cross-tab wires** (editor-illegal, editor-invisible) on every Deploy; the link-node refactor (`9ad16f7`) removed the construct entirely and the guards now enforce zero cross-tab wires forever.
- **Palette Manager module upgrades never auto-restart Node-RED.** A module can go "Upgraded" on disk (front-end static assets start serving immediately) while the live server process keeps running the old version indefinitely — no forced restart, no warning banner on the dashboard itself. If a Vue/uibuilder card stops populating right after a palette-manager notification, check `journalctl -u nodered` for an "Upgraded module … Restart Node-RED to use the new version" line before looking anywhere else.
